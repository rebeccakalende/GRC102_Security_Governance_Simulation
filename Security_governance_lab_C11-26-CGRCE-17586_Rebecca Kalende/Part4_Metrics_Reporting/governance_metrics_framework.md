# Security Governance Metrics Framework

## 1. Purpose

This framework defines how security governance performance will be measured, monitored and reported. It supports management oversight, accountability and continuous improvement.

## 2. Metrics Categories

### Implementation Metrics

- **Patch Compliance:** Percentage of systems with critical patches applied within the required timeframe.
- **Security Monitoring Coverage:** Percentage of critical systems covered by monitoring.
- **Policy Compliance:** Percentage of applicable policies implemented and followed.

### Effectiveness Metrics

- **Vulnerability Remediation Time:** Average time required to remediate critical vulnerabilities.
- **Security Incidents:** Number of recorded security incidents during the reporting period.
- **Control Effectiveness:** Percentage of tested controls that meet their defined objectives.

### Efficiency Metrics

- **Security Cost per Employee:** Security programme expenditure divided by the number of employees.
- **Automation Level:** Percentage of eligible security processes that are automated.

### Business Impact Metrics

- **Incident Cost:** Recorded cost associated with security incidents.
- **Business Disruption:** Hours of disruption attributable to security incidents.
- **Customer Impact:** Number of customers confirmed to be affected by security incidents.

## 3. Metric Definition Requirements

Each operational metric should document:

- Metric name and purpose.
- Formula and unit of measurement.
- Target and acceptable tolerance.
- Data source and collection method.
- Measurement and reporting frequency.
- Accountable owner.
- Intended management audience.
- Escalation threshold and required action.
- Evidence-retention requirements.

## 4. Data Sources

Potential sources include vulnerability scanner results, patch-management records, security-monitoring logs, incident records, governance tracker data, audit findings and control-verification results.

Data should be validated for completeness, accuracy, currency and consistency before it is included in management reporting.

## 5. Reporting Arrangements

### Operational Reporting

Security and IT teams review detailed findings, overdue remediation actions, technical exceptions and control-test results.

### Executive Reporting

Senior management reviews material risks, critical findings, remediation deadlines, control effectiveness and exceptions requiring decisions or resources.

### Board Reporting

The Board receives a concise summary of significant risks, trends, accountability, unresolved high-priority findings and progress against approved security objectives.

## 6. Metric Interpretation

Targets must reflect the purpose of each metric. Higher values are preferable for measures such as patch compliance and monitoring coverage. Lower values are generally preferable for remediation time and incident counts.

A metric should not be marked Green solely because its actual value exceeds its target. Its direction, tolerance and defined success criteria must be considered.

## 7. Metrics Lifecycle

1. Define the security objective and metric.
2. Identify the owner, data source and collection frequency.
3. Validate and calculate the measurement.
4. Compare the result with the target and threshold.
5. Report exceptions to the appropriate audience.
6. Assign corrective actions and follow up.
7. Review the metric periodically for continued relevance.

## 8. Evidence and Limitations

Metrics should be traceable to their source evidence. Simulated values must be clearly distinguished from measured results.

For this laboratory assessment, the generated trend charts use illustrative training data. They do not represent actual organisational performance and must not be used to claim that the observed technical weaknesses have been remediated.

## 9. Continuous Improvement

The framework should be reviewed periodically. Metrics, thresholds, reporting frequency and responsibilities should be updated when the risk landscape, business requirements or available evidence changes.
